# Markdown 规则书编写规范

本规范适用于 The Game Shelf 的所有桌游规则。规则书既是玩家阅读的完整正文，也是交互指南的唯一数据源。内容作者只维护 Markdown，不再创建或修改 `guide.json`、`flow.json` 或其他流程配置。

## 1. 文件与语言

- 每个游戏、每种语言只保留一份 `rules.md`：`en/rules.md` 与 `zh/rules.md`。
- 两种语言的标题结构必须完全一致：稳定 ID、层级、顺序、TAB、侧边栏和决策类型都一致；只翻译可见文字，不翻译 ID。
- 一份文档只能有一个 H1。规则正文使用 H2–H4，禁止跳级；H5/H6 不属于规则协议。
- 交互指令使用 HTML 注释，必须严格写在对应标题或列表旁边。它们是机器指令，不是给玩家看的正文。
- 普通标题、普通列表和普通链接不会自动变成交互组件。想要交互效果，必须显式添加指令。

## 2. 推荐文档骨架

```md
# Game Rules

一句话概览。

<!-- rule-section: overview -->
## 概览

<!-- rule-section: objective -->
### 游戏目标

<!-- rule-section: setup -->
## 游戏准备

<!-- rule-section: turn -->
## 回合流程
```

每个 H2–H4 前的连续结构标记中必须有一个 `rule-section` 标记；如果同时声明 TAB 或决策，`rule-ui` 放在同一组连续标记中：

```md
<!-- rule-section: turn -->
## 回合流程
```

ID 必须满足以下规则：

- 只能使用小写英文字母、数字和连字符：`[a-z0-9-]`。
- 在整份文档内全局唯一。
- 中英文文档使用相同 ID；ID 一旦发布就不要因为改标题而更换。
- 优先使用稳定、语义明确的名称，例如 `player-turn`、`scoring`、`end-game`；不要使用中文、标题自动生成的 ID 或无意义的 `section-3`。

## 3. 内容顺序与表达

每个规则块尽量按下面的顺序组织：

1. 你是谁、怎么赢：说明身份、目标和终局。
2. 你现在做什么：先用一句可执行的话告诉玩家动作。
3. 怎么做算合法：写清数量、条件、目标和限制。
4. 做完发生什么：说明奖励、结算、转交或状态变化。
5. 容易踩坑的例外：只保留会改变玩家选择的例外。

优先使用桌游口语和动作动词：

| 推荐写法 | 首次出现时可补充的正式名词 | 避免单独使用 |
| --- | --- | --- |
| 摸牌／拿牌 | 从牌堆抽取／从市场取得 | 获取一张组件 |
| 打牌／放牌 | 打出到桌面／放入自己的区域 | 执行卡牌部署 |
| 弃牌 | 放进弃牌堆 | 处置该卡 |
| 你面前的牌 | 个人区域、展示区 | 个人持有区 |
| 大家都能拿的牌 | 市场、公共区 | 可用资源池 |

- 第一段先写玩家可执行的动作，再解释术语、原因和例外。
- 标题短而具体：中文直接说动作或问题；英文使用简洁的 sentence case。
- 用有序列表表达必须按顺序执行的步骤，用无序列表表达并列选项或分类。
- 表格只用于比较选项、数值、费用和计分；不要用表格代替回合步骤。
- 不要在概览、交互指南和正文中重复同一条事实。交互组件只改变呈现方式，不应产生另一份规则来源。
- 专有行动名第一次出现时可写成“打牌（Show）”，之后优先使用中文动作词。

每个主要回合的第一句应让玩家能回答“轮到我现在做什么？”。例如：

```md
**摸 1 张 → 打 1 张。**
```

## 4. TAB

TAB 只在确实存在多个并列主题时使用；同级标题不应仅因为排版方便就拆成 TAB。

```md
<!-- rule-ui: tabs default=roll -->
<!-- rule-section: turn -->
## 回合流程

这里是所有 TAB 共用的介绍。

<!-- rule-section: roll -->
### 掷骰子

内容……

<!-- rule-section: trade -->
### 交易

内容……
```

规则：

- `tabs` 标记作用于紧随其后的父标题；父标题的直属子标题就是 TAB。
- 至少需要两个子标题。`default` 可省略，省略时打开第一个 TAB。
- 第一个子标题前的父标题内容是所有 TAB 共用的介绍。
- 每个 TAB 的内容从该标题开始，到下一个同级或更高级标题之前结束。
- TAB 标签使用短标题；不要把完整段落塞进标签。
- 禁止 TAB 套 TAB。TAB 内可以嵌套一组侧边栏或一个决策组件，但不能再嵌套第三层交互。

## 5. 侧边栏

侧边栏只转换紧随指令后的一个顶层列表。未标记的清单、组件列表、计分列表和例外条款保持普通 Markdown。

```md
<!-- rule-section: setup -->
## 游戏准备

<!-- rule-ui: sidebar default=setup-board -->
1. <!-- rule-item: setup-board -->
   **摆放版图**

   放置版图、资源和公共组件。

2. <!-- rule-item: setup-player -->
   **玩家准备**

   每位玩家领取对应组件。
```

规则：

- 每个侧边栏至少有两项；每项都必须有唯一的 `rule-item` ID。
- 每项的第一个加粗短语是菜单名称，后面的段落、图片、表格和嵌套列表是该项内容。
- 有序列表表示必须依次完成的步骤：显示序号、当前位置以及上一项／下一项。
- 无序列表表示可自由切换的分类：不显示完成进度。
- `default` 必须引用本侧边栏的某个 `rule-item`；省略时打开第一项。
- 菜单名称应是动作或短语，例如“摆放版图”“玩家准备”，不要写成长句。
- 只有真正的主题导航才使用侧边栏。普通组件清单不要添加 `rule-ui`。
- 每份规则书最多只能有一个“快速查阅”章节；固定使用 `<!-- rule-section: topic-guide -->`，不要复制出 `topic-guide-2`、`topic-guide-3` 等同名章节。

## 6. 分支决策

分支决策只用于玩家根据当前状态选择不同规则路径。循环浏览主题时使用无序侧边栏，不要伪装成决策树。

```md
<!-- rule-ui: decision start=hand-type -->
<!-- rule-section: strategy -->
## 策略助手

<!-- rule-section: hand-type -->
### 你拿到什么牌型？

<!-- rule-choices -->
- [硬牌](#hard-total)
- [软牌](#soft-total)

<!-- rule-section: hard-total -->
### 硬牌点数

规则内容……

<!-- rule-section: soft-total -->
### 软牌点数

规则内容……
```

规则：

- 决策父标题的直属子标题是节点；`start` 必须引用其中一个节点。
- 选项必须是 `rule-choices` 后紧随的无序内部链接列表；有序列表无效。
- 链接目标必须是同一决策中的节点 ID，且每个节点都必须能从起点到达。
- 允许显式循环；终点节点不写 `rule-choices`。
- 节点标题应描述玩家正在判断的问题或结果，例如“你拿到什么牌型？”，不要写成抽象的程序状态名。
- 不要把普通的 FAQ、例外说明或相关规则链接写成 `rule-choices`。
- 禁止决策套决策。决策内可以嵌套一组侧边栏，但不能再加第三层交互。

## 7. 详情、链接与媒体

### 详情折叠

`rule-details` 用于把较少使用的例外、解释或示例折叠起来。标记前的内容始终可见，标记后的内容可展开：

```md
先给出玩家必须知道的结论。

<!-- rule-details -->

这里写例外、原因或完整示例。
```

不要把完成一步所必需的条件藏进详情；玩家在默认视图中必须能完成当前动作。

### 链接

- 完整规则中的普通内部链接照常使用 Markdown 链接。
- 决策选项只能放在 `rule-choices` 列表中。
- 交互深链由系统生成：`#rule-<id>`。不要手写依赖旧格式的 `#guide-模块--条目` 链接；系统仍会兼容旧链接。

### 图片与其他 Markdown

- 图片必须服务于一个动作、组件或状态变化，并写有准确的替代文字。
- 同一游戏的中英文文档按相同顺序放置对应图片；图片路径使用项目现有的 `/images/rules/<slug>/...` 约定。
- 表格、引用、麻将短码和其他普通 Markdown 保持原样，交给现有渲染器处理。

## 8. 双语同步

编辑任一语言后，必须同步检查另一语言：

- H2–H4 的 ID、层级和顺序完全相同。
- TAB、侧边栏、决策的类型和默认项相同。
- 侧边栏项目数量与 `rule-item` ID 相同；可见菜单名称可以翻译。
- 决策节点和选项目标相同；选项文字可以翻译。
- 规则事实、限制、数字和图片不能只存在于一种语言。

## 9. 常见错误

下面这些写法会被构建校验拒绝或不会产生交互效果：

```md
<!-- 错：普通列表不会自动变成侧边栏 -->
- 摆放版图
- 玩家准备

<!-- 错：rule-choices 必须是无序列表 -->
1. [硬牌](#hard-total)
2. [软牌](#soft-total)

<!-- 错：只有一个 TAB -->
<!-- rule-ui: tabs -->
<!-- rule-section: only-one-tab -->
## 只有一个选项
```

其他高频问题：重复 ID、缺少 `rule-section`、标题跳级、错误的 `default`、决策目标不存在、决策节点不可达、把 H5/H6 当作协议标题、三层交互嵌套，以及把同一事实分别写进正文和流程配置。

## 10. 提交前自检

内容改完后，至少确认：

- 第一次阅读者只看每节第一句，也能回答“轮到我先做哪一步？”
- 每个交互指令后面紧跟正确的标题或列表。
- 中英文结构、ID、数量和顺序一致。
- 运行 `node scripts/validate-game-content.mjs`，确认 148 份规则文档全部通过。
- 代码改动时再运行 `node_modules/.bin/vitest.cmd run --config vitest.rules.config.ts`、TypeScript 检查和生产构建。
- 本地预览至少检查：默认项、TAB 切换、侧边栏深链、决策返回／重新开始、完整规则模式、移动端横向 TAB 和打印／无 JavaScript 正文。

规则页默认打开交互指南，但完整规则模式、打印和无 JavaScript 环境必须始终能看到连续完整的 Markdown 正文。交互状态不写入本地存储。
